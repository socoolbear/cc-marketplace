# worktree-setup — 여러 repo 에 걸친 작업의 공간 준비

여러 독립 repo 를 한 디렉토리 아래 모아 두는 워크스페이스를 전제한다. 그 상위 디렉토리를 이 문서에서 **우산 루트**라 부른다 — 보통 현재 cwd 이거나 그 상위에 있고, 못 찾으면 사용자에게 확인한다. **우산 루트 자체는 git 저장소가 아니다.** 하나의 이슈가 여러 repo 를 동시에 건드리면, 작업을 시작하려면 repo 마다 브랜치를 파고 worktree 를 깔아야 한다. 이 스킬은 그 준비를 한 번에 끝낸다.

산출물은 이 모양이다:

```
<우산루트>/.worktrees/<작업명>/
├── CLAUDE.md     ← 작업 루트에서 세션을 열 때 repo 규칙을 실어주는 지도
├── BRIEF.md      ← 이 작업의 출발 문서 (조사·결정·열린 쟁점)
├── <repo-a>/     ← repo A 규칙의 브랜치, origin/main 지점
└── <repo-b>/     ← repo B 규칙의 브랜치, origin/main 지점
```

## 절차

### 1. 출발점 읽기 — 링크가 있으면 원문부터

슬랙 쓰레드 링크가 주어졌으면 **추측하지 말고 원문을 읽는다.** 어느 repo 를 건드릴지, 무엇이 결정됐고 무엇이 열려 있는지가 거기 있다.

```bash
python3 <스킬디렉토리>/scripts/fetch-slack-thread.py <채널ID> <ts>
```

링크 `.../archives/C0123ABCDEF/p1712345678901234` 를 인자로 바꾸는 규칙:
- 채널 ID = `archives/` 뒤의 `C…`
- ts = `p` 뒤 숫자에서 **앞 10자리 뒤에 소수점**을 넣는다 → `1712345678.901234`

토큰은 `SLACK_TOKEN` 환경변수로 준다 (스레드 열람 권한이 있는 봇/유저 토큰).

이슈 트래커(지라 등) 링크면 열람 수단(MCP 도구·API)이 있을 때 같은 원칙으로 원문을 읽는다.

읽고 나서 **결정된 것 / 아직 열린 것을 갈라 정리한다.** 스레드는 대개 결론까지 안 가 있고, 열린 쟁점은 브랜치 이름과 작업 범위를 바꾼다.

### 2. 대상 repo 확정 — 이름이 아니라 파일로

스레드에 나온 **파일명·심볼을 실제로 찾아 repo 를 확정한다.** 서비스 이름만으로 짐작하지 않는다.

```bash
grep -rln "<스레드에 나온 심볼>" <repo> --exclude-dir=node_modules | head
find <repo> -name "<스레드에 나온 파일명>" -not -path "*/node_modules/*" | head
```

조직에 서비스명 → repo 역인덱스 도구가 있으면 그것도 활용한다.

- **모노레포는 repo 단위로 1개.** 여러 앱을 담은 모노레포라도 앱마다 worktree 를 파지 않는다 — repo 하나에 worktree 하나다.
- 확정 못 한 repo 는 넘겨짚어 파지 않는다. 사용자에게 묻는다.

### 3. repo 별 브랜치 규칙 확인 — **앱 규칙이 루트 규칙을 이긴다**

repo 마다 규칙이 다르고, 모노레포는 **앱 디렉토리의 규칙이 루트 규칙보다 우선한다.** 루트만 보고 이름을 지으면 틀린다.

```bash
cat <repo>/AGENTS.md             # 또는 CLAUDE.md
cat <repo>/<앱경로>/AGENTS.md     # 모노레포면 여기까지 반드시 (루트와 다를 수 있다)
ls <repo>/.claude/rules/          # 브랜치 표를 여기 두는 repo 도 있다
git -C <repo> branch -r --sort=-committerdate | head -20   # 문서와 실제가 다를 때의 실물 근거
```

문서에 규칙이 없으면 원격 브랜치 실물에서 다수 형식을 따른다 (예: `feat/<설명>` · `fix/<티켓번호>-<설명>`).

**정한 브랜치 이름은 만들기 전에 사용자에게 한 줄로 보고한다.** 브랜치는 PR·리뷰에 그대로 노출돼서, 만든 뒤 고치면 이미 늦다.

### 4. worktree 생성 — 절대경로로

```bash
git -C <repo절대경로> fetch origin main --quiet
git -C <repo절대경로> worktree add \
    <우산루트 절대경로>/.worktrees/<작업명>/<repo별-디렉토리명> \
    -b <브랜치명> origin/main
```

지킬 것:

- **경로는 반드시 절대경로.** `git -C <repo>` 는 cwd 를 repo 안으로 바꾸므로, 상대경로를 주면 worktree 가 `<우산루트>/.worktrees/` 가 아니라 **`<repo>/.worktrees/` 안에 생긴다.** 실제로 밟은 함정이다. 이미 잘못 만들었으면 지우지 말고 `git worktree move <잘못된경로> <올바른경로>` 로 옮긴다 (등재 정보가 따라간다).
- **지점은 로컬 `main` 이 아니라 `origin/main`.** 우산 워크스페이스의 로컬 main 은 대개 며칠 뒤처져 있다. `git -C <repo> rev-parse --short main origin/main` 로 두 값이 다른 걸 눈으로 확인하면 이유가 분명해진다.
- 디렉토리명은 repo·앱 정체가 드러나게 짧게. `.worktrees/` 에 기존 작업이 있으면 그 명명을 따른다.
- **gitignore 된 로컬 파일은 따라오지 않는다.** `git -C <repo> status --ignored --short <앱경로>` 로 본 체크아웃에 뭐가 있는지 보고, 실행에 필요한 것(`.env` 등)을 채운다. **복사보다 심링크가 낫다** — 본 체크아웃에서 값이 바뀌어도 따라가고, 두 벌이 어긋나 "본 체크아웃에선 되는데 worktree 에선 안 되는" 상황을 안 만든다. 이 작업 전용 값이 필요할 때만 복사로 바꾼다.
- `.worktrees/<작업명>/.claude/` 가 이미 있으면 **건드리지 않는다.** worktree 상위에 붙는 세션 권한 설정이라 repo 내용이 아니다.

### 5. `BRIEF.md` 남기기 — 조사한 것을 여기서 버리지 않는다

여기까지 오면 스레드를 읽고 파일을 뒤져 **repo 하나로는 안 보이는 그림**을 갖게 된다. 그 맥락이 이 세션과 함께 사라지면, 다음 세션은 같은 스레드를 다시 읽고 같은 파일을 다시 찾는다. `<우산루트>/.worktrees/<작업명>/BRIEF.md` 한 장으로 남긴다.

골격과 절별 판단 기준: `references/brief-template.md`

**위치는 작업 루트다 — 각 repo worktree 안이 아니다.** `.worktrees/<작업명>/` 은 어느 repo 의 워킹트리도 아니라서, 여기 둔 파일은 어느 `git status` 에도 안 잡히고 실수로 커밋될 일이 없다. repo 안에 두면 미추적 파일로 계속 눈에 밟히고 `.gitignore` 를 건드려야 한다. 또 이 문서는 repo 를 가로지르는 내용이라 애초에 한쪽 repo 에 속하지 않는다.

쓸 때 지킬 것:

- **확인한 것과 추측한 것을 섞지 않는다.** 코드를 열어 본 사실에는 `파일:라인` 을 달고, 근거를 못 잡은 것은 `## 미확인` 으로 내린다. 이 구분이 무너지면 다음 세션이 브리핑 전체를 못 믿고 처음부터 다시 판다.
- **원문 링크를 반드시 남긴다.** 요약은 손실이 있고, 판단이 갈릴 때 돌아갈 자리가 필요하다.
- **스레드에 결론이 없으면 없다고 쓴다.** 열린 쟁점을 임의로 닫아 적으면, 다음 세션이 그걸 합의된 결정으로 읽고 구현해 버린다. 이게 이 문서에서 가장 비싼 실수다.
- **열린 쟁점은 "첫 커밋의 방향을 바꾸는 것" 만.** 나중에 정해도 되는 세부까지 담으면 정작 막힌 지점이 묻힌다.
- 분량은 A4 한 장. 넘어가면 원문 링크에 맡기고 줄인다.

### 5-1. 작업 루트에서 세션을 열 거라면 — `CLAUDE.md` 도 같이

repo 를 동시에 건드려야 해서 **작업 루트(`.worktrees/<작업명>/`)를 세션 cwd 로 쓰는 경우**가 있다. 이때 거긴 git 저장소도 아니고 `CLAUDE.md` 도 없어서 **어느 repo 의 규칙도 안 실린다** — 커밋 scope, 검증 파이프라인, 브랜치 규칙이 전부 빠진 채로 작업이 시작된다. `<작업명>/CLAUDE.md` 를 짧게 둬서 막는다. 담을 것:

- **여긴 git 저장소가 아니라는 사실** 과 `git -C <디렉토리> ...` 격리 규칙
- `@BRIEF.md` 임포트 — 브리핑을 자동으로 실어준다
- repo 별 **규칙 문서 경로** (모노레포면 앱 지침까지. "repo 규칙이 이 지도보다 우선" 을 명시)
- **실행 전제** — worktree 에 안 따라온 gitignore 로컬 파일(`node_modules`, `.env` 등)과 채우는 방법
- 경계 — commit·push·PR 은 지시할 때만, 두 repo 를 한 커밋에 섞을 수 없음

repo 안에서 세션을 열 거면 각 repo 의 `CLAUDE.md` 가 이미 실리므로 이 파일은 필요 없다. **어디서 열 건지는 사용자에게 확인한다** — 동시 작업이 필요하면 루트, 한 repo 만 파면 그 repo 안이다.

이건 작업 인계 문서(`HANDOFF.md` 류)와 다른 문서다. 인계 문서는 **작업을 하다 만 상태**를 적어 재개용으로 쓰고, `BRIEF.md` 는 **아직 한 줄도 안 쓴 시점**의 출발 문서다. 작업이 진행되면 `BRIEF.md` 는 그대로 두고 인계 문서를 따로 쓴다 — 출발점을 진행 상황으로 덮어쓰면 "원래 무엇을 하려던 작업인가" 를 잃는다.

### 6. 확인 후 보고

```bash
git -C <repo> worktree list          # repo 마다 실행 — 등재 경로가 의도대로인지
```

보고에 반드시 담을 것:

- repo 별 **worktree 경로 · 브랜치명 · 기준 커밋**
- **어느 디렉토리에서 다음 세션을 열면 되는지** (루트면 `CLAUDE.md` 를 뒀다는 것까지)
- **`BRIEF.md` 경로**, 그리고 거기 적은 **열린 쟁점** — 사용자가 지금 답해 줄 수 있는 게 섞여 있다
- **의존성은 설치돼 있지 않다는 사실.** worktree 에는 `node_modules` 등이 없다. 빌드·테스트를 돌리려면 repo 별 설치 명령(`pnpm install` · `yarn install` · `npm install` 등)이 먼저 필요하다 — 오래 걸리므로 사용자가 필요하다고 할 때 돌린다.
- 1단계에서 갈라낸 **아직 열린 쟁점** — 그게 첫 커밋의 방향을 정한다.

## 주의

- **우산 루트에서 git 을 실행하지 않는다.** git 저장소가 아니다. 항상 `git -C <repo> ...`.
- 이 스킬은 **브랜치·worktree 생성과 루트 문서(`BRIEF.md`·필요 시 `CLAUDE.md`) 작성까지만** 한다. 코드 수정·커밋·푸시·PR 은 사용자가 따로 지시할 때만.
- repo·앱 지침이 worktree 경로를 다르게 규정한 경우가 있다. **사용자가 `<우산루트>/.worktrees/<작업명>/` 을 지정하면 사용자 지시가 이긴다** — 여러 repo 를 한자리에 모으는 게 이 배치의 목적이라서다. 다만 repo 규칙을 벗어난다는 사실은 보고에 한 줄 남긴다.
- 이미 만들어 둔 브랜치를 최신 main 에 맞추는 요청이면 이 스킬이 아니라 `worktree-refresh` 다.
